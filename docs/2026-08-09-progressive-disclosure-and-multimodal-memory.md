# 从「渐进披露」到「多模态记忆库」

2026-08-09 · 视频工作台 MCP 侧的一次收敛，以及它暴露出的下一个瓶颈

---

## 一、今天做完的:让 agent 别再一口吞下整块看板

### 病根不是「数据多」，是「不知道自己要什么之前就全拿了」

工作台的 MCP 读接口原本是这样的:agent 问一句「看看工作台」，我们把**所有页**的卡片序列化回去。一个装了十几页的工作台就是几百张卡，而用户九成时间只在看一页。更要命的是这些卡片一旦进了上下文就**待到会话结束**——它不像一次失败的工具调用可以被忽略，它是实打实占着预算的。

这轮把它拆成三层。

**第一层:范围。** `video_workbench_status` 默认只看**当前页**。要看别页得明说(`boardId` 或 `allBoards:true`)，回包带 `scope` 说清这次看到的是什么范围——否则「只看到 3 张」和「整个工作台只有 3 张」在回包里长得一模一样。

**第二层:分批。** 每页 12 → **3 张**。一张卡的 JSON 约 500 token，12 张就是六千 token 一次灌进来，而 agent 通常只关心其中一两张。

**第三层:目录。** 这层是前两层能成立的**前提**，也是最容易被漏掉的一层。

只回 3 张却不告诉 agent 剩下的是什么，它只能从第 1 页翻到最后一页——调用次数翻十倍，省下的上下文全赔进往返里，而且每次往返用户都在干等。所以加了 `pageIndex`:覆盖整个范围、一页一条，只带该页的卡片 id 和每条提示词的开头 24 字。

```json
"pageIndex": [
  { "page": 1, "cardIds": ["c1","c2","c3"], "digest": "夜景追车起势 / 车内特写 / 撞击瞬间" },
  { "page": 2, "cardIds": ["c4","c5"],      "digest": "医院走廊 / 病房对话 [succeeded]" }
]
```

一条约等于四分之一张卡。**读目录挑页，再取那一页**——或者直接拿目录里的 `cardIds` 点名，连翻页都省了。

目录本身也封了 30 条上限。不封的话 200 张卡按 3 张一页就是 67 条，目录自己又变成一次性倒出去——那等于把刚堵上的洞换个地方重开。

### 页面摘要:目录之上还缺一层索引

分批读取解决了「一页之内」，但**跨页**仍然是瞎的:别页在目录里只剩 `id / name / cardCount`，而页名十有八九就是「页面 3」。「20 张卡」判断不了要不要翻过去。

所以给每一页加了一句话摘要(`video_workbench_set_board_summary`)，随 boards 目录一起回读:

```
追车 · 夜外 · 主角车vs追兵
```

限 **60 字**、电报体。这个数字不是随手定的:摘要跟着 boards 在**每一次**工作台调用里回传，十页就是十条——写成句子的话十条能顶掉一整屏上下文，而它本来是用来省上下文的。**一个比它救下的卡片还贵的摘要，等于自我否定。** 60 字够写电报体、不够写一段话，这个约束本身就是在逼出正确的格式。

超限**拒绝而非截断**。截断看着更友好，实际是切在半个词上，agent 拿到成功回执还以为完整写进去了。

摘要也做进了 UI:别页的截断显示在页签上，当前页的在页签栏**右侧空域**完整显示，单击展开、双击编辑。放右侧而不是撑宽当前页签，是因为撑宽会让切页时所有页签左右跳。用户能自己写/改/清空——否则 agent 标错了改不掉，是个单向门。

### 顺带修的两类「不报错的错」

**写操作白写。** `apply` 撞车时原本只回一句「版本变了，请重新导出整板」。现在回带该卡的**当前现场**并点明**哪几个字段对不上**。另外，值没变的 `updateCard` 不再 bump 版本号——输入框失焦提交同样的值很常见，白让 agent 手里的数据失效不值。

**工具行为没声明。** 23 个 MCP 工具没写 `ToolAnnotations`，客户端只能按最坏情况理解，导致多余的确认弹窗。补齐时发现两处我自己判错了:`add_tasks` 会触发老卡淘汰、`update_task` 换模型时会截断素材，**两者都是破坏性的**，之前标成了 additive。

### 同一天的看图链路

- **一次看多张图**(`file_urls` / `file_paths`)。这不是省调用次数，是**能不能做到**的问题——模型把同一次请求里的多张当成一组看，「这两张是同一个人吗」才答得了;拆成多次它每次只看见一张。追加图并发中转但**按输入序落位**(顺序即身份)，任一张失败整条报错、不静默跳过(少一张会让后面所有序号前移而模型察觉不到)。
- **PDF 修好了**。此前对所有「文档」一律发 `image_url`，一个指向 `.pdf` 的 `image_url` 上游读不出内容——工具说明里那句「先渲成图效果最好」就是这么来的:**不是上游不行，是我们发错了形状**。
- **`fps` 是个死字段**。类型上早就声明，组请求体时被丢掉，等于永远走默认 2.0。
- **接上 `qwen3.8-max`**(`model="flagship"`)，默认仍是 plus——两者视频规格完全相同，旗舰的价值在 1M 上下文与推理强度。
- **Gemini(apiyi)通道不再暴露**。启用判据是「有没有 key」而不是「key 能不能用」，失效的 key 与有效的长得一模一样，agent 看见工具就去用、连撞三次才知道不行。这比工具不存在更糟。

## 二、今天没解决的:所有这些都是「读取侧的止血」

上面每一条都在回答同一个问题——**怎么少读一点**。但没有一条回答了更根本的那个:

> **为什么 agent 需要「读」才能知道?**

现在的形态是:所有状态散在渲染层 zustand + IndexedDB 里，agent 想知道任何事都得**发起一次工具调用把数据搬进上下文**。分页、目录、摘要都是在优化这次搬运的体积——但搬运本身还在。

而且这只是工作台一处。真实的制片项目里，同时活着的东西远不止卡片:

| 数据 | 现在住在哪 | agent 怎么找到它 |
|---|---|---|
| 角色卡 / 人像库 | 上游素材 API + 本地 overlay | 列表工具，全量拉 |
| 场景图 / 分镜图 | 文件系统 + COS | 靠路径，agent 得自己记 |
| 剧本 / 批次拆解 | markdown 文件 | 全文读进上下文 |
| 演出方向 / 讨论 / 计划 | **散在历史会话里** | **基本找不回来** |
| 视频卡片 / 提示词 / 进度 | IndexedDB | 分页读(今天刚做) |
| 成片 / 素材 | 本地盘 + COS | 靠路径 |

最后一列暴露了真正的问题:**这些东西之间的关系无处安放。** 「第 6 镜用的是林浩川的第 2 版角色卡，那版是在 8 月 3 号那次讨论里定的，因为用户说第 1 版太年轻」——这条链路今天完全不存在，每次都要靠人重述一遍。

**渐进披露把「读得太多」压下去了，但压不出「记得住」。**

## 三、下一步:多模态记忆库

目标不是「换个地方存数据」，而是让 agent **按需检索而不是全量读取**，并且**跨会话记得住关系**。

### 深挖后的结论:主体数据别上云,只把 embedding 上云

深挖之后，**我推翻了自己第一版的建议**。原本打算主体数据上 Lindorm，查了连接方式和计费之后发现这条路对**桌面应用**根本走不通。

**硬约束一:Lindorm / ADB 都连不上桌面客户端。**

Lindorm 向量引擎兼容 Elasticsearch 协议(端口 30070，Node 端可以直接用 `@elastic/elasticsearch` 或裸 HTTP)——这部分很友好。但访问方式只有两种:

- **专有网络 VPC** — 要求应用部署在 ECS 上。我们是装在用户电脑里的 Electron。
- **公网地址** — 需要在控制台**逐个开通**，并且**把访问设备的公网 IP 加进白名单**。

第二条对桌面应用是死路:每个用户的公网 IP 都不一样、还会变，不可能维护白名单。更糟的是数据库用户名密码得塞进客户端——那等于把库交出去。

要绕开只有一条路:**自建一个后端代理**。但我们现在没有自己的后端(Miau 是第三方网关)，为一个记忆库去起一套服务、扛鉴权和多租户，成本远超收益。

**硬约束二:Lindorm 没有 Serverless，是常驻集群。**

计费是按节点 CPU / 内存 / 存储累加(`cpu单价 × cpu数量 × 节点数量 × 时长`)。也就是说**不用也在烧钱**。桌面应用的使用是突发的、按人分散的，常驻集群的成本模型和它完全不匹配。

**而我们本地已经有一个能装向量的库了。**

`package.json` 里已经有 `@electric-sql/pglite`(0.4.5)和 `@electric-sql/pglite-socket`，构建链里也有 `build-pglite-worker.mjs`——**Postgres 跑在 WASM 里，已经随包发出去了**。PGlite 支持 `pgvector` 扩展，也就是说:关系表 + 向量检索 + 全文，一个本地库全有，而且:

- 零凭据、零白名单、零后端
- **离线可用**——这是桌面应用的硬需求，不是加分项
- 数据留在用户机器上，不涉及素材上云的合规问题
- 边际成本为零

**所以方案变成:存储和检索留在本地 PGlite，只把「把图片/文本变成向量」这一步交给阿里云。** 后者是**无状态 HTTP 调用**，用我们已有的 `DASHSCOPE_API_KEY`，不需要任何网络配置。

### embedding 选型(这一步确实该用阿里)

查了百炼的向量模型表，四个候选差别不小:

| 模型 | 维度 | 图片上限 | 单次图片数 | 图片单价(每千 token) |
|---|---|---|---|---|
| `tongyi-embedding-vision-plus` | 1152 | 3MB | **8 张** | **¥0.0005** |
| `tongyi-embedding-vision-flash` | 768 | 3MB | 8 张 | ¥0.00015 |
| `multimodal-embedding-v1` | 1024(固定) | 3MB | **1 张** | ¥0.0009 |
| `qwen3-vl-embedding` | 2560(可降到 256) | 10MB | — | ¥0.0018 |
| `text-embedding-v4` | 64–2048 | 纯文本 | — | ¥0.0005(Batch ¥0.00025) |

**选 `tongyi-embedding-vision-plus`(图) + `text-embedding-v4`(文)。** 理由:

- 老牌的 `multimodal-embedding-v1` **单次只能传 1 张图**，给一个分镜项目建索引要发几百次请求;vision-plus 单次 8 张，还更便宜。
- `qwen3-vl-embedding` 维度高(2560)、图片上限大(10MB)，但贵 3.6 倍，且高维度意味着本地索引更占空间。角色卡和分镜图这种用途，1152 维够了。
- 文本走 `text-embedding-v4`:维度可调(建议 1024)，**Batch 调用半价**——首次给存量剧本建索引时能省一半。

有一个概念别搞混:这些模型分**融合向量**和**独立向量**两种用法。我们要的是**独立向量**(每张图一个向量)，因为用途是"找相似参考图";融合向量是把图文合成一个向量，用于图文整体匹配。

### 那阿里的数据库还有用武之地吗

查了阿里云开发者社区和 GitHub，三条路各有归属:

有，但**不是现在，也不是这个位置**。

**Lindorm(多模一体)** — 一套系统内宽表 / 向量 / 时序 / 全文 / 文件五种模型，向量与全文索引共享底层存储、不用双写;官方数字是单 Key 读写 P99 < 1ms、向量检索 P99 < 10ms。技术上确实是同类里最省心的。
→ **但它的形态是给服务端应用用的。** 只有当我们真的有了自己的后端(比如做云端协作、多设备同步、团队共享素材库)，它才成立。那时候它替代的是 Milvus + ES + Redis 三套拼接，价值很大。**现在没有那个前提。**

**AnalyticDB for PostgreSQL(长记忆)** — 提供 `ADBPG LLM Memory Manager`，**向量 + 知识图谱双存储**:向量存记忆内容，图存关系追踪。明确支持**多模态记忆抽取**(直接给图片 URL，多模态 LLM 解析后入库)，兼容 Mem0 生态。
→ **值得盯住的是它的「双存储」思路，不是它的实例。** 「角色卡 ← 定于哪次讨论 ← 因为什么反馈」这条链需要图结构，而 PGlite 本身也是 Postgres——同样的表结构和递归 CTE 在本地就能做。**先在本地把图建起来，验证 agent 用不用得上;真到了数据量或协作需求扛不住，再整体搬到 ADB-PG，schema 基本不用改**(这是选 PGlite 而不是 SQLite 的关键理由)。

**百炼长期记忆 API / PolarDB Mem0** — 全托管，零部署。**这条是唯一现在就可以直接用的云侧选项**，因为它是 HTTP API 不是数据库连接，没有白名单问题。缺点是记忆内容存在云上、且是它自己的抽取逻辑，可控性低。
→ 可以作为**对照组**:本地方案做完后，拿同一批数据对比召回质量，验证我们自己的分型和检索是不是真的够用。

**Tablestore** 在大规模向量检索和混合搜索上不如前两者，需要额外配向量库，不考虑。

### GitHub 侧:自维护记忆的几条硬经验

Mem0 的架构文档和社区实践里有几条直接适用:

1. **别用一个扁平的记忆池。** 用 metadata 给记忆分型(`preference` / `task_state` / `feedback` / `project`)，检索时按类型过滤，而不是盲目语义搜索。有人实测这一条让每轮召回的 token 降了约 40%。
2. **在读路径上做过期，不是靠定时任务。** 「进行中」这类状态记忆最容易变陈旧，读的时候按时间过滤掉，存储自动保持干净，预算也不会无界增长。
3. **`feedback` 类记忆无条件注入，不要语义召回。** 「别再把角色写年轻」这种纠正，如果靠语义碰运气召回，就会时灵时不灵。
4. **作用域要显式。** Mem0 用 `user_id` / `agent_id` / `run_id` / `app_id` 四维隔离，缺省时只返回全为空的那批，防止串味。我们对应的是**项目 / 剧本 / 页 / 会话**四层。
5. **Mem0 2026 年 4 月的新算法改成了「只增不改」** —— 单次 LLM 调用只做 ADD，不做 UPDATE/DELETE，记忆累积而非覆盖;检索侧用语义 + BM25 + 实体三路并行融合，外加时间感知排序。这个取舍值得借鉴:**写入侧越简单越不容易出错，复杂度放到检索侧**。

### 分阶段计划

**阶段 0:先把关系记下来(不引入任何云服务)**

在动数据库之前，先解决「关系无处安放」。今天已经有了页面摘要这个雏形——它证明了「一句话索引 + 随目录回读」这个形态是work的。把它推广:

- 给角色卡、场景、分镜图各加一条 `provenance`(这东西是哪来的、为什么是这样)
- 用 sidecar 文件(`.meta.json`)挂在素材旁边，跟着文件走，不依赖任何服务
- 验证一件事:**agent 真的会去读这些索引吗?** 如果它宁可全量扫描，那说明索引的粒度或触发时机不对——这个问题在本地就能暴露，不必等上云。

**阶段 1:PGlite + pgvector 起本地库(不引入任何新依赖)**

PGlite 已经在包里了，这一步的增量只有 schema 和一层查询封装。

- 表:`project` / `script` / `shot` / `character` / `asset` / `decision`，外键连起来——**这是今天最缺的「关系」**。
- 向量列用 pgvector，先只索引两类:**角色卡图**和**分镜图**(找参考图是最高频的诉求)。
- embedding 走 `tongyi-embedding-vision-plus`(图) / `text-embedding-v4`(文)，用已有的 `DASHSCOPE_API_KEY`，无状态调用、不需要任何网络配置。
- 首次建索引用 `text-embedding-v4` 的 **Batch 接口**(半价)。
- 关键设计:**embedding 结果落库**，同一张图不重复算。素材本身不动(仍在本地盘 / COS)，库里只存路径 + 向量 + 元数据。

**阶段 2:把「讨论 → 决定」记下来**

这是今天完全丢失、价值最高的部分。

- 记忆分型(Mem0 经验第 1 条):`decision` / `feedback` / `character` / `shot_state`。用**表 + 枚举列**实现，不是一个扁平的向量池。
- `feedback` 类**无条件注入**(第 3 条)，不走语义召回——「别再把角色写年轻」靠语义碰运气会时灵时不灵。
- `shot_state` 类在**读路径**上按时间过滤(第 2 条)，避免陈旧的「进行中」被当成现状读回。
- **验收标准要能证伪**:挑一个两周前的项目，问 agent「第 6 镜为什么是现在这样」，看它能否答出因果链，而不是复述当前状态。答不出就是分型或触发时机不对，继续在本地改——这个循环在本地是分钟级的，上了云就是小时级。

**阶段 3(有前提才做):云端**

触发条件明确写死，不满足就不启动:

- **多设备 / 团队协作**成为真实需求 → 这时才需要服务端，Lindorm 的多模一体价值才兑现。
- **本地库规模扛不住**(比如向量超过百万级) → 迁 ADB-PG，因为 PGlite 就是 Postgres，schema 和 SQL 基本可以直接搬。
- 在此之前，云侧只用**无状态的 embedding API**，不碰数据库。

### 要先想清楚的三件事

**1. 阶段 0 不能跳。** 上云解决的是「存得下、查得快」，解决不了「该记什么」。如果本地 sidecar 阶段就发现 agent 不主动读索引，那上了 Lindorm 也只是把不读的数据换个地方放。

**2. 别让数据库变成第二个「全量读取」。** 今天的教训是:给了检索能力，agent 未必会精准检索——它可能 `SELECT *`。所以工具层要**继续**限制返回体积和分页，数据库只是让「精准查询」成为可能，不是自动发生。

**3. 离线是硬约束。** 这是个桌面应用，用户在没网的地方也要能开工。本地 PGlite 天然满足;唯一需要联网的是**新素材的 embedding 计算**——没网时应当**入库但标记为待索引**，联网后补算，而不是拒绝入库。

**4. 选 PGlite 而不是 SQLite，是为了留一条上云的退路。** 两者本地体验差不多，但 PGlite 就是 Postgres——真要迁到 ADB-PG 时 schema、SQL、pgvector 用法几乎原样可用。SQLite 到 Postgres 的迁移则要重写一遍。这个选择今天不花钱，将来省一次重写。
