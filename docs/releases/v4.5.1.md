# v4.5.1 发行说明

> 更新渠道:腾讯云 COS 热更新(`releases/latest.yml`)+ GitHub Release 存档
> 上线版本:v4.5.0

## 概述

补丁版,只补构建产物,**不改任何运行时代码**:把 Codex 0.147 升级时漏掉的两个
同级可执行文件装进安装包,并加上守护防止同类遗漏再次发生。

用户侧的表现是 code mode 不再报「找不到程序」。

## 补上两个同级二进制

codex 从**自己所在目录**拉起 helper 可执行文件(`bundled_executable_path_for_exe()`),
所以少一个同级二进制不是「功能降级」,是每次调用都弹一个 Windows「找不到
程序」—— 即便在 `danger-full-access` 下也一样。

升级到 0.147 时上游新增了 `codex-code-mode-host`(54.8 MB)和
`codex-responses-api-proxy`(5.7 MB),我们没跟上。**构建全程是绿的**,缺口
一直到用户让模型跑 code mode 才暴露出来,4.5.0 仍然缺这两个。

## 守护:让下次不会再静默漏掉

光补两条只修这一次。真正的问题是「上游新增了二进制」这件事**没有任何信号**——
自动升级 PR 只给已经在册的条目换哈希,从不去发现新增的资产。

新增 `assertNoUnlistedCodexBinaries`:发现任何既不在打包列表、也不在显式跳过
列表里的 `codex-*-<triple>.exe` 就让 fetch 失败并点名。把「我们忘了」变成一次
构建失败,而不是一个只在用户机器上出现的错误。

`codex-app-server`(236 MB)进显式跳过列表并写明理由:它能用
`codex.exe app-server` 走到,单独打包会让安装包差不多翻倍却不带来任何新能力。
此前这条只是「挑主二进制时别选错」的消歧义过滤,现在成了记录在案的决定。

## 顺带

- 修一条时序 flake:`CodexProtocolClient.clientUserMessageId` 的 steer 用例等的
  是「服务端收到 turn/start」,而 `steer()` 要求客户端已从**响应**写入
  `turnIdByThread`,中间隔一个 ws 往返。改为等真前置状态,并在假服务端加 30ms
  刻意延迟 —— 同步回包时竞态窗口接近零,这也是它只在 CI 上炸、本地无法复现的
  原因。
- 顺带堵掉三处悬空 `iterator.next()` 在 teardown 时产生的未处理 rejection:
  vitest 会因此判整轮失败,哪怕每条断言都过。
