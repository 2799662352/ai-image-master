# v4.9.23 发布说明

> 更新渠道:腾讯云 COS 热更新(`releases/latest.yml`)+ GitHub Release 存档
> 上线版本:v4.9.22

## 概述

两件事:**① Codex 页 DeepSeek(Miau)通道的模型次序调整,以及后台「记忆 / 会话自动起标题」改用火山标准版模型;② 移除应用内置的 apiyi(Gemini)MCP。**

## 变化

- **模型选择器次序**:DeepSeek 组现在按 `火山 V4.1 Flash` → `火山 V4.1 Flash 经济版` → `DeepSeek V4 Pro` → `DeepSeek Flash` 排列(火山在前,官方在后,`V4 Pro` 排在 `Flash` 前面)。只是次序变了,模型本身和各自的参数没动;已有的选择不受影响,通道默认对话模型仍是 `deepseek-flash`。
- **移除内置的 apiyi(Gemini)MCP**:桌面端不再内置、不再启动它(它早已对 agent 隐藏,能力与千问 omni 的 `understand_*` 工具重复),也不再往 `~/.codex/config.toml` 写 `[mcp_servers.apiyi]`。老用户配置里应用当年种下的那一条会在首次启动时自动清掉(只认指向应用自带路径的条目,你自己写的同名条目、解析失败的配置文件都不碰),日志里会有一行 `[apiyi-mcp] legacy entry cleanup: removed`。顺带修掉了「全新的 Codex 目录下报 `invalid transport in mcp_servers.apiyi`、Codex 起不来」的问题(旧写法在配置里没有这张表时会凭空造出一张没有 transport 的表)。**API易作为 Codex 网关 / 出图站点不受影响**;设置里已保存的 API易 key 也保留。`catimation-understand` 技能里「apiyi-mcp 作深度复核备选」那一节同步删除;自己服务器上独立部署的 apiyi MCP(`deploy/` 下)不受影响。
- **记忆与会话自动起标题改用火山标准版**:这个通道的四个模型(火山两个 + 官方两个)的后台记忆提取 / 合并和自动起标题,统一走 `deepseek-v4-1-flash-261017`(原来是 `deepseek-flash`)。统一成一个值,是因为记忆模型在启动 Codex 时就固定了、同一通道内切换模型不会重启,按模型分路会在切换后用错模型。

## 注意

- **官方两个模型(`DeepSeek V4 Pro` / `DeepSeek Flash`)的后台记忆和起标题也会按火山标准版计费**。同一时段它的单价是 `deepseek-flash` 的 6.7 倍。按 2026-10-30 网关扣费日志的实测:一次记忆提取约 ¥0.07,一次记忆合并(约 99 万输入 token、97% 命中缓存)约 ¥0.22,**一次完整整理合计约 ¥0.3**;同样的工作用 `deepseek-flash` 按倍数推算约 ¥0.045(推算值,未实测)。合并只在有新的提取结果时才跑,频率取决于你开新会话的节奏,这些费用会出现在用量明细里。(此前草稿里写的「单次约 ¥0.0005、绝对值很小」只按一条很小的请求估的,是低估。)

## 已验证

- **火山标准版记忆,对生产网关跑通(2026-10-30,真实内置 Codex + 本机转发代理)**:聊天模型 `deepseek-flash`,记忆模型 `deepseek-v4-1-flash-261017`。阶段 1(提取)HTTP 200、返回合法结构化结果、落库、任务 `done`;阶段 2(合并)同一模型连续 24 次请求全部 HTTP 200,任务 `done`(约 130 秒),写出 `MEMORY.md` / `memory_summary.md` / `raw_memories.md` 与一个自动生成的技能。
- **模型选择器次序**:主进程的模型目录由真实的 `AgentManager` 处理函数按 `toEqual` 精确断言(火山标准版 → 火山经济版 → `deepseek-v4-pro` → `deepseek-flash`)。
- **apiyi 旧配置清理**:8 条测试在临时目录的真实文件上跑(清掉应用种的条目、保留用户自己的同名条目、解析失败不改写、幂等)。

## 还没覆盖的地方

- **没有在真实窗口里看新版的选择器次序和首次启动的 apiyi 清理。** 开发窗口无法与你真实的 `~/.codex` 隔离(Electron 不认用户目录重定向),所以没有起;选择器次序上午在窗口里看过一次,但那次走的是渲染层的备用目录,不是主进程目录。升级后请看一眼日志里的 `[apiyi-mcp] legacy entry cleanup` 行和选择器次序。
- **记忆验证样本很小**:只有一份 rollout、从空记忆库起步的整理,没有测多份 rollout 的增量合并,也没有评估合并产出的质量(只确认文件写完、任务 `done`)。
- 有一次运行里阶段 1 请求撞上一次瞬时 `fetch failed`(5 秒),Codex 自动重试后成功,没有查网络层原因。
- 验证脚本曾在 Codex 被强杀后留下一条「合并任务 running、租约 1 小时」的记录,第二个进程 10 分钟内没有接手;正常退出不会留下它,**用户强杀应用后的下一次启动是否同样 1 小时内合并不了,没有单独验证**。
