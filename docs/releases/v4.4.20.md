# v4.4.20 发布说明

> 发布渠道:腾讯云 COS 热更新(`releases/latest.yml`)+ GitHub Release 兜底
> 基线版本:v4.4.19

一次修复版本,清掉的三件事里有两件是 4.4.19「已知未做」里点过名的。

## 上传不再替上游猜体积

一张 6.4MB 的参考图会报「COS relay upload failed (`[object Object]`)」,并建议你压到
512KB 以下。这两句话都不对:512KB 只是「内联还是走中转」的分界,压到它以下只是绕开
中转;而 `[object Object]` 意味着失败的真实原因一个字都没露出来 —— 腾讯 COS SDK 抛
的是裸对象而不是 Error,调用方那句 `String(e)` 就渲成了这样。

**客户端的体积闸门全部撤掉**,交给上游裁决 —— 上限是上游的裁量,写死在客户端只会在
它放宽时误伤你,而真超限时上游本来就会给出确切数字:

| 位置 | 原来 | 现在 |
|---|---|---|
| 主进程本地素材 | 50MB 硬限,整文件读进内存 | 无上限,分片流式上传 |
| 卡片粘贴兜底 | 30MB 直接拒 | 无上限 |
| 人像库自动导入 | 图 30MB / 视频音频 50MB | 无上限 |
| 人像库页上传 | 图 30MB / 视频 50MB | 无上限,且改传真实路径而非 base64 |

视频与音频 **4–15s 的时长校验保留** —— 时长超了这文件根本用不了,本地一测就知道,
拦下来省一次上传;体积正相反。

## 传不上去时,现在说得清为什么

- 任何 COS 失败都渲成人话,带上错误码、HTTP 状态、内层网络原因(DNS/TLS 只在内层说
  真话)和 requestId。
- **瞬时失败自动重试**:5xx、429 限流、408 超时、连接被掐、DNS 抖动,退避是指数 +
  抖动并封顶 8 秒。鉴权与请求错误立即放弃 —— 那类重试只是把失败推迟。抖动不是装饰:
  批量启动时几十张卡同时上传,一起撞上服务端抖动后,固定退避会让它们继续步调一致地
  重试。
- **同一份素材不再有两种命运**。此前从本地路径进来的中转失败直接报错,从剪贴板进来的
  却会悄悄降级回内联,表现是「同一张图有时报错有时能过」。现在两条入口共用一套降级
  策略:体积还在上游限内就降级内联(公司网络只放行部分域名、COS 不可达而模型接口可达,
  是真实场景),超出就报错并带上原因。

素材库下载(`download_portrait_asset`)也改成流式落盘,与上传方向口径一致,300MB 那道
自定上限随之取消。要提醒一句:这个工具真正的约束是**时间**不是体积 —— 它由 Codex 调用,
工具超时 60 秒,我们在 45 秒主动收口,所以去掉体积上限并不意味着能拉一个超大文件回来。

## 未出片的卡拖进聊天栏,不再什么都不发生

此前会被一句提示拦下,拖过去等于白拖。现在按产物存活性逐级降级,和播放器同一顺序:
本地 mp4 还在就走附件加引用;只剩耐久地址就把 URL 写进输入框(视频 URL 走不了引用通道,
模型根本看不见,那等于假装递了东西);真没有产物就合成一份 Markdown 规格说明作为附件,
里面带 cardId,模型可以直接调工作台工具改这张卡。

顺带修掉一个误判:判断「有没有产物」早先只看本地路径,而本地 mp4 会被 7 天清理扫走
(卡片对那个清理是隐形的),于是云端还在、播放器照样能放的卡会被说成「还没有生成结果」。

拖卡片时聊天栏现在有投放高亮 —— 此前连已出片那条成功路径都是盲拖。

## 开发版与安装版不再撞端口

`os error 10048` 这条已知问题的根因不在端口分配,在单实例锁的守卫缺失:拿不到锁的那个
实例只调了 `app.quit()`,而它是异步的 —— 初始化照常跑完,注册 IPC、拉起 agent、绑
PGlite 的 5433、绑 MCP 端口、spawn codex 全都做了一遍。也就是说「输掉的那个实例」在
退出前会把共享资源全摸一遍。守卫补上了。

另一半在端口选择:探测「端口空闲」只能证明那一刻是空的,而 codex 要等进程起来才占用,
中间的窗口关不掉。旧实现从 4222 顺序扫描,两个实例同时开工必然双双选中 4222 —— 实测
连取 20 次全是 4222。现在改为区间内随机起点,并且撞了就换端口重来(只对端口冲突重试,
二进制缺失、配置错误这类立刻原样抛出)。

## 验证

- 全量单测与 typecheck 债务闸随 CI 执行;新增用例均先写失败测试再实现。
- 重试策略的分类口径对齐 AWS SDK 与 `@google-cloud/storage` 的公开实现,包括
  「408/429 虽是 4xx 但可重试」这条 —— 原先「4xx 一律终态」会把限流当成永久失败。
- `ports.ts` 此前零测试,这次补了 12 条。

## 已知未做

- 同一份素材每次重新生成都会重新中转上传一遍(Key 是随机的,没有内容寻址),中转桶也
  没有清理规则。功能上无影响,但会积累冗余对象。
- 批量启动时上传并发没有上限;主进程另一条上传链路已有 4 路闸门,这条还没复用。
- 大文件上传全程没有进度反馈,卡片只显示「正在准备素材…」。
- 素材传到一半取消不掉:卡片在拿到 taskId 之前只能记下取消意图。
- 剪贴板粘贴的合成文件仍在渲染端转 base64(系统拖拽与文件选择器都带真实路径,走不到
  这条路)。
- 开场视频偏长(65.8s),尚未裁剪。
- 本地数据库「卡死」而非「退出」时不会自动恢复,只能靠 30 秒池超时兜住。
- 崩溃瞬间在飞的写不会重试,只有读会。
- 图片生成仍无任务恢复(上游无异步任务 ID)。
